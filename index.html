Talk about a routine Five-minute architecture

The work changed seats

You still babysit every send, because the account still lives in someone’s head — the client, the rule, what happens next. Drafting moved to the bot. The watching did not.

The work changed seats

Retrieval moved the reading. Relatedness did not. Embeddings answer what text is nearby; they cannot follow a defined link or inherit a rule from a type. Call time is still reconstruction — in your head, or in a prompt you re-type.

The context is scattered

Your routines are stable. The context around each run is not.

Answering is cheap

A bot that drafts from the knowledge base is a prompt and a folder. Agencies already have that.

Acting needs a babysitter

Send, file, book — someone who holds the account in their head still checks every step, or the agent just finishes.

Changing the steps is a deploy

Who approves, what waits on a file: that lives in a zap or in code. Ops can see it. Ops cannot edit it.

The reconstruction stack

You already know each layer. The failure is that they do not share a model.

Info vs action

Q&A is retrieval. A write needs a bound principal, a tool, and a stop. Silent policy violations have no tool error.

HITL is bolted on

Slack, interrupt(), a second task system. Resume state and required parameters get reinvented per integration.

The graph is code

LangGraph and filter stacks can draw a flow. Changing a branch is a release. Operators cannot open the artifact agents run.

One workspace. This account.

A private workspace where what things mean, the records, and the work share one model.

Someone on the team names the client, the approver, and the rule once. After that the producer and the assistant use the same ones. If the file is not here yet, the same piece of work holds.

It does not invent the file. It does not finish last hour’s retainer.

One model. Three node kinds.

SCHEMA is the contract. INSTANCE is a record that satisfies it. STEP is an executable unit. A sequence is a walk of guarded POINTS_TO edges. Nested payloads sit in SQLite; the graph holds relationships and routing.

The path through the graph is the explanation.

Example: campaign approval

The run reads this account. It may ask this approver. It may follow this brand rule. A missing file pauses the run — it does not guess.

Not a smarter search over your docs. A neighborhood you can walk, and a gate a human still owns.

  1. Read this account
  2. Ask this approver
  3. Follow this brand rule
  4. Wait — file not here yet

Same primitive, three transports

Dashboard, POST …/sequences/{id}/run, and /api/spaces/{id}/mcp share one executor. Required parameters return pending and a state_id. A clock is waiting — not a form.

Keep n8n for connectors. Use this when the next step depends on what the record is.

  2. HTTP sequence webhook
  3. Agent MCP tool = the sequence
  4. Pause pending + state_id

How we’d show it

How we’d show it

The process is the walk — not a SOP in Notion plus a zap. We do not map the whole agency. We map what one routine touches.

SCHEMA / INSTANCE, then STEP, then the same sequence on three doors. Bounded — not a CMS of everything.

  1. 1. Map a little

    Client, approver, rate, brand rule, file — the nodes that approval actually uses. Not teams, discounts, and the whole org chart.

    A handful of SCHEMA nodes and the INSTANCE neighborhood for one account. Traversal, not top-k.

  2. 2. Map the walk

    Onboarding or campaign approval as a chain that reads those nodes, branches, and pauses for a person.

    STEPS joined by guarded POINTS_TO. Changing who approves is an edge condition — not a deploy.

  3. 3. Same run, three doors

    A button on a dashboard, an assistant with the same routine as a tool, or an API call from something you already have.

    UI, webhook, MCP. One sequence_service. Authoring MCP writes the same builder snapshot.

Who this is for

For

Agency owners and ops leads whose week is still kickoff / revision / approval / publish from memory — and who have already tried letting an assistant take a step.

Teams whose agents need related, governed context, not only retrieved prose. Operators who need to change a rule without a deploy. One artifact that is a dashboard workflow, a webhook, and an MCP tool.

Not for

A hundred SaaS connectors and no domain model (keep the glue tool). An agent you are still inventing (a notebook is cheaper).

Warehouses, Zapier-scale connector catalogs, or exploratory LangGraph with no stable types yet. GraphRAG on documents is not a runnable HITL sequence.
